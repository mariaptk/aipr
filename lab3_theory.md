## 1. Устройство лабораторной

Сервер один — **Tomcat**. В нём развёрнуто одно веб-приложение `lab3_servlet` с двумя сервлетами.
База H2 отдельным сервером не является: это файл, который сервлет открывает изнутри Tomcat.
Клиентов два: браузер со страницей `dictionary.html` и отдельная Java-программа `lab3_client`.

```text
Проект 1: lab3_servlet  (сервер, работает в Tomcat)
├── Web Pages
│   ├── dictionary.html          стартовая страница с формой
│   └── WEB-INF
│       ├── web.xml              какие сервлеты и по каким адресам
│       └── images/picture.jpg   рисунок для варианта 2
├── Source Packages / com.mycompany.lab3_servlet
│   ├── MyServlet.java           сервлет-словарь
│   ├── DictionaryDb.java        работа с базой данных
│   └── ImageServlet.java        сервлет, отдающий рисунок
└── pom.xml                      зависимости: Jakarta EE и драйвер H2

Проект 2: lab3_client  (обычное Java-приложение с окном)
├── Lab3_client.java             окно, запросы к MyServlet по URL
└── pom.xml                      зависимость: Apache HttpClient

База данных: файл C:\Users\user\lab3dict.mv.db
```

```text
 Браузер ─────────┐
 (dictionary.html) │   HTTP-запрос
                   ├──────────────►  Tomcat (порт 8080)
 lab3_client ──────┘                  └── приложение /lab3_servlet
 (окно Swing)                              ├── MyServlet ──► DictionaryDb ──► база H2
                   ◄──────────────         └── ImageServlet ──► picture.jpg
                     HTTP-ответ
```

### Основные понятия

| Понятие | Что это |
|---|---|
| Tomcat | веб-сервер: принимает HTTP-запросы на порту 8080 |
| Веб-приложение | серверный проект в Tomcat, адрес `http://localhost:8080/lab3_servlet/` |
| Сервлет | Java-класс в веб-приложении, отвечает на запросы по своему адресу |
| Клиент | тот, кто отправляет запрос: браузер или Java-программа |
| HTTP | протокол обмена между клиентом и сервером |
| JDBC | стандартный способ работы Java с базами данных |
| H2 | встроенная база данных, хранит данные в файле |

Как клиент находит сервлет: `localhost` — этот компьютер, `8080` — порт Tomcat,
`/lab3_servlet` — приложение, `/MyServlet` — сервлет.

### Что происходит при переводе

1. Браузер отправляет `GET /lab3_servlet/MyServlet?txt=кот&trans=&dir=ru-en`.
2. Tomcat по `web.xml` находит `MyServlet` и вызывает `doGet`, а тот — `processRequest`.
3. Сервлет читает параметр `txt` и вызывает `DictionaryDb.toEnglish("кот")`.
4. База выполняет `SELECT` и возвращает `cat`.
5. Сервлет формирует HTML со значением `cat` и отправляет его браузеру.

Обратный перевод работает так же, но с `dir=en-ru` и вызовом `toRussian`.

Java-клиент отправляет `GET .../MyServlet?format=text&dir=ru-en&txt=кот`.
Из-за `format=text` сервлет возвращает не HTML, а одно слово `cat`.

Рисунок: ссылка `ImageServlet` → сервлет читает `picture.jpg` и отвечает байтами с типом `image/jpeg`.

## 2. Сервлет

**Сервлет** — серверный Java-класс, который выполняется внутри веб-контейнера (Tomcat),
принимает HTTP-запрос через объект `request` и формирует ответ клиенту через объект `response`.

Сам по себе сервлет не запускается и сервером не является: его создаёт и вызывает веб-сервер.

Сервлет наследуется от `HttpServlet`.

### Жизненный цикл

| Метод | Когда вызывается | Что делает в лабе |
|---|---|---|
| `init()` | один раз при загрузке сервлета | `DictionaryDb.init()` создаёт и заполняет базу |
| `doGet()` | при каждом GET-запросе | передаёт работу в `processRequest` |
| `doPost()` | при каждом POST-запросе | передаёт работу в `processRequest` |
| `destroy()` | один раз при остановке | не переопределён |

### Объекты запроса и ответа

- `HttpServletRequest request` — запрос клиента. `request.getParameter("txt")` читает поле формы `txt`.
- `HttpServletResponse response` — ответ клиенту:
  - `setContentType(...)` — тип ответа;
  - `getWriter()` — текстовый поток для HTML и текста;
  - `getOutputStream()` — байтовый поток для файлов;
  - `setHeader(...)` — заголовки ответа.

### Сервлеты в лабе

**`MyServlet`** — словарь. Читает `txt`, `trans`, `dir`, ищет перевод в базе.
При `format=text` отвечает одним словом, иначе возвращает HTML-страницу с формой и результатом.

**`ImageServlet`** — вариант 2:

- `getServletContext().getResourceAsStream("/WEB-INF/images/picture.jpg")` открывает файл;
- `getMimeType(...)` определяет тип по расширению: `.jpg` → `image/jpeg`;
- `Content-Disposition: inline` — показать рисунок в браузере, `attachment` — скачать файлом;
- байты пишутся в `getOutputStream()`, потому что рисунок — двоичные данные, а не текст;
- файл лежит в `WEB-INF`, поэтому напрямую по адресу его не открыть, только через сервлет.

### Отличия от методички

- Импорты `jakarta.servlet`, а не `javax.servlet`: Tomcat 10 и новее используют Jakarta EE.
- Библиотеки подключаются через Maven в `pom.xml`, а не скачиваются вручную.
- `dictionary.html` лежит в Web Pages, а не в `WEB-INF`: из `WEB-INF` браузер файлы не открывает.

## 3. GET и POST

Два основных метода HTTP-запроса. Определяют, как клиент передаёт данные серверу.

| | GET | POST |
|---|---|---|
| Где данные | в адресе после `?` | в теле запроса |
| Видны в адресной строке | да | нет |
| Объём | ограничен длиной адреса | практически не ограничен |
| Назначение | получить данные | отправить или изменить данные |
| Метод сервлета | `doGet` | `doPost` |

Пример GET:

```text
http://localhost:8080/lab3_servlet/MyServlet?txt=кот&dir=ru-en
```

Метод задаёт атрибут формы:

```html
<form method="get" action="MyServlet">
```

В лабе форма и Java-клиент (`HttpGet`) используют GET, поэтому срабатывает `doGet`.

Формулировка методички: при GET данные передаются одним сообщением вместе с заголовком,
при POST — отдельно. Точнее: при GET данные входят в строку адреса в заголовке запроса,
при POST идут в теле запроса.

## 4. Файл web.xml

**web.xml** — дескриптор развёртывания. Сообщает серверу, какие сервлеты есть в приложении
и по каким адресам они отвечают. Лежит в `WEB-INF`.

```xml
<servlet>
    <servlet-name>MyServlet</servlet-name>
    <servlet-class>com.mycompany.lab3_servlet.MyServlet</servlet-class>
</servlet>
<servlet-mapping>
    <servlet-name>MyServlet</servlet-name>
    <url-pattern>/MyServlet</url-pattern>
</servlet-mapping>

<welcome-file-list>
    <welcome-file>dictionary.html</welcome-file>
</welcome-file-list>

<session-config>
    <session-timeout>30</session-timeout>
</session-config>
```

| Тег | Назначение |
|---|---|
| `<servlet>` | связывает имя сервлета с Java-классом |
| `<servlet-mapping>` | связывает имя сервлета с URL-адресом |
| `<welcome-file-list>` | стартовая страница приложения |
| `<session-config>` | время жизни сессии без активности, в минутах |

`action="MyServlet"` в форме попадает в класс `MyServlet` именно через эти записи.

## 5. База данных и JDBC

Требование задания «используется база данных, содержащая переводы слов» означает:
переводы лежат в таблице базы и ищутся SQL-запросом, а не записаны в коде (`HashMap`, `if`).

### Как устроено в лабе

- Адрес базы `jdbc:h2:~/lab3dict`, файл `C:\Users\user\lab3dict.mv.db`.
- `Class.forName("org.h2.Driver")` загружает драйвер.
- `DriverManager.getConnection(URL, "sa", "")` открывает соединение.
- `init()` создаёт таблицу `words` и, если она пустая, добавляет 10 пар слов.

| Колонка | Что хранит |
|---|---|
| `id` | номер записи, автоматически |
| `rus` | русское слово |
| `eng` | английский перевод |

Прямой и обратный перевод:

```sql
SELECT eng FROM words WHERE LOWER(rus) = LOWER(?)   -- toEnglish
SELECT rus FROM words WHERE LOWER(eng) = LOWER(?)   -- toRussian
```

- `LOWER` — поиск без учёта регистра.
- `?` — параметр. `PreparedStatement` подставляет слово безопасно, без склейки SQL-строки.
  Это защита от SQL-инъекций.
- Если слова нет, метод возвращает `null`, сервлет пишет «нет в словаре».

Основные объекты JDBC: `Connection` (соединение), `Statement` / `PreparedStatement` (запрос),
`ResultSet` (результат запроса, он же курсор).

## 6. Курсоры

**Курсор** — указатель на текущую строку в результате SQL-запроса.
Запрос может вернуть много строк, программа читает их по одной.

В Java курсор — объект `ResultSet`:

```java
try (ResultSet rs = ps.executeQuery()) {
    return rs.next() ? rs.getString(1) : null;
}
```

- после `executeQuery()` курсор стоит **перед** первой строкой;
- `rs.next()` сдвигает его на следующую строку, возвращает `false`, если строк больше нет;
- `rs.getString(1)` читает первую колонку текущей строки.

Чтение многих строк:

```java
while (rs.next()) {
    System.out.println(rs.getString("rus") + " - " + rs.getString("eng"));
}
```

### Виды курсоров по перемещению и видимости изменений

| Вид | Как двигается | Видит изменения в таблице | Скорость |
|---|---|---|---|
| Последовательный (forward-only) | только вперёд | изменения в ещё не прочитанных строках | самый быстрый |
| Статический | в любую сторону | нет, работает со снимком | быстрый, нужна память под копию |
| Ключевой (keyset) | в любую сторону | изменения и удаления да, новые строки нет | средний |
| Динамический | в любую сторону | да, все изменения | самый медленный |

Статический, ключевой и динамический курсоры называют **прокручиваемыми** (scrollable).

### Другие деления

- **По изменению данных:** только для чтения (read-only) и обновляемые.
- **По тому, кто создаёт** (Oracle PL/SQL): неявные создаёт база для каждого запроса,
  явные объявляет программист.
- **По месту хранения:** серверные и клиентские.

Явный курсор (диалект SQL Server):

```sql
DECLARE words_cursor CURSOR FOR SELECT rus, eng FROM words;
OPEN words_cursor;
FETCH NEXT FROM words_cursor;
CLOSE words_cursor;
DEALLOCATE words_cursor;
```

### Курсоры в JDBC

```java
PreparedStatement ps = c.prepareStatement(sql,
        ResultSet.TYPE_SCROLL_INSENSITIVE,
        ResultSet.CONCUR_READ_ONLY);
```

| Константа | Смысл |
|---|---|
| `TYPE_FORWARD_ONLY` | последовательный, только `next()` |
| `TYPE_SCROLL_INSENSITIVE` | прокручиваемый, не видит изменений (близок к статическому) |
| `TYPE_SCROLL_SENSITIVE` | прокручиваемый, видит изменения (близок к динамическому или ключевому) |
| `CONCUR_READ_ONLY` | только чтение |
| `CONCUR_UPDATABLE` | обновляемый |

В `DictionaryDb` тип не задан, поэтому курсор **последовательный и только для чтения**.

## 7. Буфер и кэш

**Буфер** — временная область памяти, где данные лежат, пока передаются между устройствами,
программами или потоками.

### Четыре назначения буфера

1. **Нивелировка (сглаживание) скоростей.** Источник и приёмник работают с разной скоростью.
   Буфер накапливает данные, быстрая сторона не ждёт медленную на каждом байте.
2. **Асинхронный ввод-вывод.** Программа кладёт данные в буфер и сразу продолжает работу,
   обмен с устройством идёт параллельно.
3. **Согласование размеров блоков данных.** Стороны работают порциями разного размера.
   Буфер собирает мелкие порции в нужный блок или делит большой на части.
4. **Семантика копирования.** Данные копируются в буфер в момент записи. Если программа потом
   изменит переменную, уйдёт версия на момент записи.

Пример: `BufferedReader` собирает байты из сокета и отдаёт их строкой через `readLine()`.

### Кэш

**Кэш** — быстрая память с копией часто используемых данных, чтобы не обращаться каждый раз
к медленному источнику. Примеры: кэш процессора, кэш браузера.

| | Буфер | Кэш |
|---|---|---|
| Что хранит | данные в пути, пока их не заберёт получатель | копию данных для повторного использования |
| Зачем | согласовать передачу | ускорить повторный доступ |

## 8. Прерывания

**Прерывание** — сигнал процессору о событии, которое требует внимания прямо сейчас.
Процессор приостанавливает текущую работу, выполняет обработчик прерывания и возвращается
к прерванной программе. Благодаря этому процессору не нужно постоянно опрашивать устройства.

### Виды по источнику

- **Аппаратные** — от устройств: клавиатура, сетевая карта, диск, таймер.
- **Программные** — программа сама обращается к ОС, например чтобы открыть файл.
- **Исключения** — ошибка при выполнении команды, например деление на ноль.

### Маскируемые и немаскируемые

| | Маскируемые | Немаскируемые (NMI) |
|---|---|---|
| Можно ли запретить | да | нет |
| Источник | обычные устройства ввода-вывода | критические аппаратные события |
| Примеры | клавиатура, таймер, сеть, диск | ошибка памяти, сбой питания, watchdog |
| Обработка | можно отложить | сразу |

Маскируемые прерывания запрещают на время критического участка кода, который нельзя прерывать
посередине. У x86 для этого команды `CLI` (запретить) и `STI` (разрешить).

## 9. Процесс и поток

**Процесс** — выполняющаяся программа вместе с выделенными ей ресурсами: своей памятью,
открытыми файлами, сетевыми соединениями. Процессы изолированы друг от друга.

**Поток** — последовательность команд, которая выполняется внутри процесса. Потоки одного
процесса работают одновременно и используют его общую память и ресурсы.

| | Процесс | Поток |
|---|---|---|
| Что это | выполняющаяся программа | исполнитель внутри процесса |
| Память | своя, изолированная | общая с потоками процесса, свой только стек |
| Ресурсы | свои | общие с потоками процесса |
| Как общаются | через ОС: сеть, файлы, каналы | через общие переменные |
| Создание и переключение | дольше | быстрее |
| Если упал | другие процессы работают | может уронить весь процесс |
| Сколько | программа — минимум один процесс | в процессе минимум один поток |

Примеры из лаб:

- **Потоки, лаба №2:** поток окна, поток сервера `Account`, потоки клиентов `UiClient` в одной
  программе меняли общую переменную `amount`.
- **Процессы, лаба №3:** Tomcat и `lab3_client` — разные процессы, общей памяти нет,
  поэтому они общаются по HTTP.

В Java поток — наследник `Thread`: код задачи в `run()`, запуск через `start()`.
`start()` создаёт новый поток, прямой вызов `run()` нового потока не создаёт.

**Коротко:** процесс владеет памятью и ресурсами, поток их использует и выполняет код.

## 10. Контекст процесса и контекст потока

**Контекст** — то, что ОС сохраняет при переключении, чтобы потом продолжить работу
с того же места.

### Контекст процесса

1. **Адресное пространство** — память процесса: код, данные, куча.
2. **Таблица дескрипторов** — открытые файлы, сокеты и другие ресурсы.
   Дескриптор — номер, по которому процесс обращается к ресурсу.
3. **PID** — уникальный номер процесса в ОС.

Служебные данные для планировщика: приоритет и использованное процессорное время.

Классическое деление (UNIX): пользовательский контекст (код, данные, куча, стек),
регистровый контекст (регистры процессора), системный контекст (запись в таблице процессов,
таблицы памяти, открытые файлы, стек ядра).

### Контекст потока

1. **Значения регистров**, в том числе счётчик команд — адрес следующей команды.
2. **Регистр флагов** — состояние процессора после последней операции.
3. **Маски** — какие прерывания (сигналы) сейчас запрещены для потока.
4. **Указатель на стек** — у каждого потока свой стек.

Также служебная информация: идентификатор, состояние, приоритет потока.

**Почему потоки переключаются быстрее:** при смене потока одного процесса меняются только
регистры, флаги, маски и указатель стека. При смене процесса нужно сменить ещё адресное
пространство и ресурсы.

## 11. Стек и куча

### Стек

**Стек** — область памяти для данных вызовов: параметры, локальные переменные,
адрес возврата. Принцип LIFO: последним пришёл — первым ушёл.
У каждого потока свой стек, память освобождается при выходе из метода.

**Два основных назначения стека:**

1. **Вызов подпрограмм.** В стек кладутся адрес возврата, параметры и локальные переменные.
   После выхода всё снимается, программа продолжает с адреса возврата.
2. **Обработка прерываний.** Процессор сохраняет в стек адрес прерванной команды, флаги
   и регистры. После обработчика значения снимаются, программа продолжает с того же места.

Благодаря LIFO вложенные вызовы и вложенные прерывания возвращаются в правильном порядке.

Переполнение стека в Java — `StackOverflowError` (например, слишком глубокая рекурсия).

### Куча

**Куча** (heap) — область памяти для объектов, созданных через `new`. Общая для всех потоков
процесса. Объекты живут, пока на них есть ссылки; освобождает память **сборщик мусора**.
Нехватка памяти — `OutOfMemoryError`.

Пример: `new Socket(...)` создаёт объект в куче, а переменная `s` со ссылкой на него лежит в стеке.

| | Стек | Куча |
|---|---|---|
| Что хранит | локальные переменные, параметры, ссылки | объекты, созданные через `new` |
| Чей | свой у каждого потока | общая для потоков процесса |
| Освобождение | автоматически при выходе из метода | сборщиком мусора |
| Ошибка при нехватке | `StackOverflowError` | `OutOfMemoryError` |

## 12. Контрольные вопросы

**1. Что такое сервлет, какие основные объекты и методы он предоставляет?**
Java-класс, который работает внутри веб-сервера и обрабатывает HTTP-запросы. Наследуется от
`HttpServlet`. Методы: `init()`, `doGet()`, `doPost()`, `destroy()`. Объекты:
`HttpServletRequest` (данные запроса, `getParameter`) и `HttpServletResponse`
(`setContentType`, `getWriter`, `getOutputStream`).

**2. Как сервлет определяется в клиентском сайте?**
Атрибутом `action` формы: `<form action="MyServlet" method="get">`. Кнопка `submit`
отправляет форму, Tomcat находит сервлет по адресу из `web.xml`. От `method` зависит,
вызовется `doGet` или `doPost`.

**3. Для чего служит web.xml, какая у него структура?**
Дескриптор развёртывания: описывает сервлеты и их адреса. `<servlet>` — имя и класс,
`<servlet-mapping>` — имя и URL, `<welcome-file-list>` — стартовая страница,
`<session-config>` — время жизни сессии.

**4. Как вернуть результаты сервлета клиенту?**
Через объект `response`. Для HTML — `setContentType("text/html;charset=UTF-8")`, затем
`getWriter()` и `out.println(...)`. Для файла — например `setContentType("image/jpeg")`
и запись байтов в `getOutputStream()`.

## 13. Дополнительные вопросы на защите

- **Сколько серверов?** Один — Tomcat. В нём одно веб-приложение с двумя сервлетами.
- **Где отдельный клиент?** Проект `lab3_client`: свой `main`, свой `pom.xml`, обращается
  к сервлету по URL. При остановленном Tomcat пишет «Нет связи с сервером».
- **Почему `jakarta.servlet`?** Tomcat 10+ работает на Jakarta EE, пакет переименован.
- **Где хранится база?** В файле `C:\Users\user\lab3dict.mv.db`, таблицу создаёт `init()`.
- **Зачем `PreparedStatement`?** Параметр `?` защищает от SQL-инъекций.
- **Почему рисунок в `WEB-INF`?** Оттуда браузер файлы не открывает, их отдаёт только сервлет.
- **Зачем `format=text`?** Java-клиенту нужен только перевод, а не HTML-страница.
- **Зачем `URLEncoder.encode`?** Чтобы русские буквы корректно передавались в адресе.
- **Почему `getWriter()` для HTML, а `getOutputStream()` для рисунка?** Первый — текстовый
  поток, второй — байтовый, а рисунок является двоичными данными.
- **Чем лаба №3 отличается от лабы №2?** В №2 клиент и сервер общались напрямую через сокеты,
  протокол придумывали сами. В №3 общение идёт по HTTP, а приём соединений, разбор запроса
  и вызов нужного класса делает Tomcat.
